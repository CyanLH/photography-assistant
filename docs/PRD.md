**위치·시간 주의:** 현재 웹 프로토타입의 로컬 시간 표시와 날짜 경계는 기기 시간대를 사용한다. 사용자가 멀리 떨어진 해외 좌표를 수동 입력할 때 해당 좌표의 IANA 시간대가 자동 추정되는 것은 아니다. 실제 서비스에서는 Google Maps Time Zone API 또는 위치→IANA 시간대 변환 어댑터로 선택 위치 기준 날짜/시간을 계산하고 DST를 검증해야 한다. 고위도에서 태양 고도 경계 통과가 없으면 숫자를 만들어내지 않고 '해당 날짜에 없음'으로 표시한다. 태양·달 값은 근사 천체력 기반 예측값이며 기상, 지형, 건물 차폐 여부를 알지 못한다.

## 1. 제품 정의

Photography Assistant는 촬영자의 위치와 선택한 시각, 태양·달의 위치, 기상 예보, 촬영 의도, 센서 크기와 렌즈를 결합해 ‘어느 방향에서, 무엇을, 어떤 빛으로 찍을지’를 설명하는 모바일 우선 웹앱이다. 미러리스 사용자가 기본 대상이며 스마트폰 사용자는 보조 프로필로 수용한다. 스마트폰 카메라를 켜거나 미러리스와 연결할 필요가 없다.

**해결할 질문**
- 지금 이 자리에서 노을·인물·풍경·달 중 무엇을 시도할 만한가?
- 카메라의 광축을 어느 방위로 향하게 해야 하는가? 그 이유는 무엇인가?
- 지금 찍는 것과 30분 뒤 찍는 것 중 무엇이 더 유리한가?
- 내가 가진 렌즈와 삼각대로 어떤 구도가 가능한가?

**제품이 약속하지 않는 것**
위치와 기상 정보만으로 아름다운 피사체, 열린 시야, 접근 가능한 장소, 실제 장면의 노출값을 알 수 없다. 따라서 ‘좋은 사진 보장’, ‘노을 성공률 92%’, ‘AI가 찾은 안전한 촬영 명소’ 같은 표현은 사용하지 않는다. 추천은 빛의 기하와 예보에 근거한 촬영 조건 제안이다.

**핵심 사용자 흐름**
앱 실행 → 위치 허용 또는 지도에 촬영자 핀 설정 → 촬영 의도 선택 → 추천 방위와 근거 확인 → 보유 장비에 맞는 시작 설정 확인 → 휴대폰의 참고 방향을 확인하고 카메라를 별도로 정렬 → 촬영 또는 시간 계획 저장.

**초기 검증 목표 — 제품 목표이지 측정 결과가 아님**
권한·장비 초기 설정 이후 3회 이내 조작으로 첫 추천에 접근한다. 사용성 테스트에서 ‘내가 보는 방향’과 ‘태양이 있는 방향’을 혼동하지 않는지, 추천의 이유를 사용자가 설명할 수 있는지 확인한다. 지표는 추천 열람률·방향 안내 사용률·계획 저장률·추천 유용성 평가이며 정확한 위치를 분석 이벤트에 포함하지 않는다.

## 2. 사용자와 촬영 시나리오

| 사용자 | 상황 | 필요한 도움 |
|---|---|---|
| 미러리스 풍경 촬영자 | 낯선 장소에 도착해 해질 무렵의 구도를 찾음 | 태양 방향, 순광/측광/역광 후보, 남은 빛의 시간 |
| 인물 촬영자 | 모델과 공원·거리에서 촬영 | 역광과 측광 배치, 얼굴 노출 주의, 피사체 이동을 고려한 셔터 우선순위 |
| 망원·달 촬영자 | 달을 풍경 또는 건물과 함께 촬영 | 달의 고도·방위·위상, 렌즈 화각, 위치 이동이 필요한지 판단 |
| 초보 교환식 카메라 사용자 | 날씨 앱의 수치를 사진으로 연결하기 어려움 | 전문 수치의 쉬운 설명과 조건부 시작 설정 |

‘일반적으로 서쪽이 좋다’라는 하나의 답을 만들지 않는다. 같은 태양 방위에서도 노을은 태양 쪽, 순광 풍경은 반대쪽, 측광 풍경은 옆쪽을 향하는 후보가 달라진다. [S1]

## 3. 범위와 우선순위

### P0 — 첫 출시
1. 위치: 사용자 동작 후 Geolocation 1회 요청, 재탐색, 지도 수동 핀 또는 위경도 입력. 위치 거부와 실내 실패도 정상 사용 경로로 제공한다. [S2]
2. 천문: 태양·달 방위각/고도, 일출·일몰, 월출·월몰의 존재 여부, 달 위상/밝은 면 비율, 제품 정의 골든·블루 구간, 시간 이동.
3. 기상: 온도, 운량(가능하면 하층/중층/상층), 강수확률/강수량, 풍속/돌풍, 시정. 미제공 값은 null이며 0으로 대체하지 않는다. [S4]
4. 촬영 의도: 노을·풍경·인물·달. 풍경은 순광/측광, 인물은 역광/측광을 추가 선택할 수 있다.
5. 설명 가능한 추천: 방위, 범위, 가능한 빛, 유리한 점, 제약, 데이터 품질, 렌즈/지지 조건별 설정 우선순위.
6. 빛 지도: 촬영자 핀과 선택적 피사체 핀, 태양/달 방향선, 촬영 시야 부채꼴, 선택 시각. 지도는 이동 경로를 계산하지 않는다.
7. 시간 계획: 향후 24시간을 기본 범위로 하며, 예보가 제공되는 경우 최대 72시간까지 탐색. 위치의 시간대를 명시한다.
8. 장비: 센서 가로/세로 크기, 실제 초점거리, 렌즈 최대 개방값, 삼각대, 피사체 움직임. 카메라 모델명은 자유 입력이며 필수가 아니다.
9. 저장: 로컬 장비·촬영 계획 저장/삭제. PWA 설치 및 마지막 데이터 확인은 지원하되 오프라인을 실시간으로 보이지 않게 한다.

### P1 — 검증 이후
지도 장소 검색·공유 링크·프레이밍 크기 계산 보강·여러 장비 프리셋·촬영 후 간단한 피드백·국내 관측/특보 어댑터·불확실성 보정·분석에 동의한 익명 사용성 이벤트.

### P2 — 별도 검증이 필요한 기능
지형과 건물 차폐, DEM 기반 지평선, 3D 지형에서 달/태양과 랜드마크 정렬, 선택적 AR 미리보기, 장비별 연결, 고급 은하수 모드. 푸시 알림은 브라우저/PWA 제약을 검증한 뒤 추가한다. API나 모델이 없는 상태에서 기능이 있는 것처럼 표현하지 않는다.

### 초기 제외
카메라 원격 제어, 촬영 이미지 업로드, AI 사진 점수, 주변 피사체 자동 인식, 소셜 피드, 계정/결제, 자동 동선 추천, 날씨를 근거로 한 안전 보장.

## 4. 정보 구조와 화면 계약

### S01 시작·권한
가치 제안 한 문장 → ‘현재 위치 사용’ → 요청 이유 → 브라우저 권한. ‘지도에서 직접 선택’을 동등하게 노출한다. 나침반 권한은 사용자가 ‘방향 맞추기’를 눌렀을 때 따로 요청한다. 화면을 여는 즉시 여러 권한 팝업을 연속해서 띄우지 않는다. [S2][S3]

### S02 현장 가이드 — 홈
상단: 장소명 또는 위경도, 선택 시각/시간대, 현재·미리보기·오프라인 구분.
중앙: 촬영 의도 탭, 북쪽 고정 나침반, 태양/달 위치, 추천 촬영 방위, 화각 범위.
설명: ‘서남서 258° 방향으로 카메라를 향하세요’ + ‘태양을 화면 뒤에 두는 역광 구도’ 등 행동과 이유. 표시 각도는 참고값이며 센서가 부정확하면 범위와 상태를 우선한다.
보조: 날씨 근거, 촬영 시작 설정, 대안 1~2개, 시간 슬라이더.
주 행동: ‘방향 맞추기’. 보조 행동: ‘빛 지도에서 보기’, ‘이 시간 저장’.

### S03 방향 맞추기
현재 휴대폰 참고 방위, 목표 카메라 방위, 최소 회전 방향을 크게 표시한다. ‘휴대폰과 카메라는 별개입니다’라는 안내를 유지한다. 헤딩 지원이 없거나 신뢰하기 어려우면 수동 회전/지도 기준 모드로 전환한다. 휴대폰을 평평하게 잡는 모드와 화면 회전 보정을 명확하게 정의한다. 실물 카메라 방향이 자동으로 추적되는 것처럼 표현하지 않는다.

### S04 빛 지도
촬영자 핀과 피사체 핀의 역할을 색+아이콘+텍스트로 구분한다. 태양선은 빛의 기하, 부채꼴은 렌즈 화각, 촬영선은 카메라→피사체 방위이다. 모든 선에 범례를 제공한다. 지도 회전 시 north-up/head-up 상태를 표시한다. GPS 정확도 원은 위치 오차이지 방위 오차가 아니다. ‘방향선은 이동 경로가 아님’, ‘지형·건물 차폐 미반영’을 표시한다.

### S05 시간 계획
선택 위치의 날짜·시간대, 태양 고도 곡선, 제품 정의 골든/블루 구간, 구름·강수·바람 변화, 월출/월몰을 한 화면에 맞춘다. 슬라이더는 천문값을 부드럽게 갱신하지만 시간별 예보를 분 단위 관측값으로 만들지 않는다. 저장한 계획은 위치·시각·촬영 의도·장비 snapshot을 포함하며 로컬에 저장한다.

### S06 내 장비
‘미러리스’를 기본 촬영 장비로 제시한다. 센서 프리셋은 풀프레임 36×24 mm, 일반 APS-C 23.5×15.6 mm, Canon APS-C 22.3×14.9 mm, MFT 17.3×13 mm, 직접 입력을 제공한다. 프리셋은 모델별 실제 크기를 대체하지 않으므로 상세 장비에서 수정할 수 있다. 렌즈 초점거리는 실제 mm로 입력한다. 35mm 환산값과 실제 초점거리를 같은 필드에 섞지 않는다.

### S07 추천 상세
추천 조건과 제약, 사용한 데이터 기준 시각, 선택 장비, 노출 시작점의 가정, 다른 방향 후보, 실패/보류 이유를 제공한다. 같은 좌표와 입력에서는 같은 규칙 결과를 반환한다.

## 5. 미러리스 전용 설계

카메라 브랜드 DB보다 **센서·렌즈·촬영 지지 조건**을 우선한다. 촬영자가 풀프레임 24–70mm 줌을 가지고 있다면 현재 설정 초점거리 35mm를 별도로 선택한다. 최대 개방값은 조리개 후보의 하한이며 줌 구간별 최대 개방이 달라지는 렌즈는 해당 구간의 값을 사용한다.

수평 화각 = 2 × atan(유효 센서 가로 길이 / (2 × 실제 초점거리)). 각도 출력은 degree로 변환한다. 풀프레임 35mm 렌즈의 수평 화각은 약 54.4°, 200mm는 약 10.3°다. 이 값은 직선 투영 렌즈의 기하적 근사이며 왜곡·포커스 브리딩·디지털 크롭은 별도다. 세로 구도에서는 센서 가로/세로를 교환한다. 전자식 크롭이나 영상 모드를 사용하는 경우 유효 센서 크기에 반영한다.

달을 크게 찍으려면 초점거리뿐 아니라 피사체와 촬영자의 거리 및 정렬이 중요하다. 대략적인 달의 각지름은 약 0.5°이므로 풀프레임 200mm 가로 프레임에서 달은 폭의 약 5% 수준에 불과하다. ‘200mm면 달이 화면을 가득 채운다’는 설명을 금지한다. 정확한 각지름 계산은 천문 어댑터의 거리와 선택한 상수를 사용해 검증한다. [S8]

### 촬영 설정은 정답이 아니라 시작점
| 의도 | UI에서 제안할 우선순위 | 반드시 함께 표시할 가정 |
|---|---|---|
| 노을/정적 풍경 | A/Av, F5.6–F8 후보, 낮은 ISO, 셔터는 카메라 측광으로 결정 | 삼각대 유무, 바람과 피사체 움직임, 하이라이트 확인 |
| 역광 인물 | 원하는 심도에 맞는 조리개, 피사체 움직임을 멈출 최소 셔터, Auto ISO 후보 | 얼굴 노출과 하늘 보존은 절충; 보조광 유무를 모름 |
| 블루아워 | 삼각대가 있으면 낮은 ISO와 긴 셔터 후보, 없으면 손떨림을 피하는 셔터 우선 | 손떨림 보정 성능을 브랜드만으로 추정하지 않음 |
| 달 | 충분한 초점거리, 달 표면 하이라이트 점검, 시험 촬영 후 조정 | 대기·위상·고도·크롭·흔들림에 따라 달라짐 |

F값·셔터·ISO를 동시에 확정해 ‘적정 노출’이라고 표시하지 않는다. 수치가 필요하면 고정값이 아닌 시작 범위와 가정을 제공한다. IBIS가 있어도 움직이는 피사체가 멈추는 것은 아니다. 휴대폰 카메라는 선택 가능한 별도 장비 모드이며, 직접 노출 설정을 지원하지 않는 기기는 조언 수준을 낮춘다.

## 6. 추천 엔진

### 6.1 좌표·각도 계약
위도/경도는 WGS84 decimal degrees. 방위각은 항상 진북 0°, 동 90°, 남 180°, 서 270°이며 시계 방향이다. 고도는 수평선 0°, 천정 +90°다. SunCalc v2의 현재 문서는 degree와 북쪽 기준 방위를 반환한다. v1 예제의 radian→degree/+180° 변환을 v2 결과에 적용하면 오작동한다. 설치 버전을 확인하고 lockfile에 고정하며 어댑터 밖에서 변환하지 않는다. [S1]

```
normalize360(x) = ((x % 360) + 360) % 360
signedDelta(target, heading) = ((target - heading + 540) % 360) - 180
angleDistance(a, b) = abs(signedDelta(a, b))
```

signedDelta가 양수이면 오른쪽(시계 방향), 음수이면 왼쪽이다. 목표 1°, 현재 359°는 오른쪽 2°다. 정확히 180° 차이는 어느 방향으로 돌아도 같으므로 ‘반대 방향’으로 표시한다.

### 6.2 촬영 방향 정의
추천 방위는 **카메라에서 피사체로 향하는 광축 방향**이다. 빛이 진행하는 벡터와 반대로 혼동하지 않는다. 태양의 방위를 A라고 하면:
- 태양/노을을 바라보는 역광 후보: A.
- 태양을 촬영자의 뒤에 두는 순광 후보: normalize360(A + 180°).
- 측광 후보: normalize360(A + 90°), normalize360(A - 90°).
- 달 촬영 후보: 달의 방위와 고도. 달과 랜드마크의 겹침은 피사체 핀/높이 및 지형 정보가 없으면 확정하지 않는다.

위 관계는 태양이 피사체 거리보다 매우 멀다는 근사 아래의 기하적 제안이다. 실제 얼굴 방향·건물 면 방향·나무 그늘·주변 반사광은 알 수 없으므로 ‘현장에서 확인’을 항상 허용한다.

### 6.3 처리 순서
입력 검증 → 시간대/선택 시각 확정 → 천문 계산 → 날씨 정규화 → 가능한 후보 생성 → 후보별 제약/보류 판정 → 장비 적합성 검사 → 설명과 대안 생성.

**먼저 걸러야 할 상태**
- 달 고도가 0° 이하: ‘기하학적 수평선 아래’로 표시하고 달 직접 촬영을 추천하지 않는다. 실제 지평선/차폐 때문에 0° 위여도 보이지 않을 수 있다.
- 태양이 수평선 아래: 직접 태양광을 전제로 한 순광/측광 인물 추천은 중단하고 잔광·실루엣·도시 조명으로 전환한다. 저녁 하늘색 가능성과 태양 자체 가시성은 구분한다.
- 기상 결측/오래된 예보: 천문만 제공하며 좋은 날씨라고 추론하지 않는다.
- 흐린 예보: 태양 방향선은 유지하되 직접광 효과를 단정하지 않는다. 운량만으로 실제 광량을 계산하거나 노을의 색을 보장하지 않는다.
- 매우 낮은 달/태양: 열린 시야와 대기 영향 경고를 제공한다. 낮 동안의 달은 무조건 제외하지 않고 밝은 하늘 대비의 한계를 설명한다.
- 악천후 가능성: 촬영 추천보다 주의 메시지를 먼저 보여준다. 일반 기상값으로 공식 특보를 생성하지 않는다.

### 6.4 제품 기본 임계값 — 관측적 진리가 아님
골든 구간은 태양 고도 0°~6°, 블루 구간은 -6°~-4°를 초기 UX 정의로 사용한다. 사진가마다 정의가 다르므로 제품 설정임을 명시하고 추후 조절 가능하게 한다. 위도와 계절에 따라 해당 구간의 길이가 달라지며 ‘한 시간’으로 고정하지 않는다. [S1]

v1에는 성공 확률이나 100점 점수를 표시하지 않는다. 결과 수준은 ‘추천 / 조건부 / 보류’, 데이터 품질은 ‘충분 / 일부 부족 / 오래됨’을 별도로 표기한다. 숫자 점수가 필요한 후속 버전은 검증 데이터와 calibration 이후 도입하며 사진 품질 확률이라고 부르지 않는다.

### 6.5 출력 계약
추천은 `{id, intent, directionDeg, directionRangeDeg, altitudeDeg?, lightType, suitability, reasons[], caveats[], gearAdvice[], dataQuality, sourceTimes, ruleVersion}`를 반환한다. 추천 후보가 없으면 빈 결과와 구체적인 이유를 반환한다. LLM은 P0 필수가 아니다. 향후 LLM은 계산된 결과를 문장으로 다듬는 데만 사용하며 방위·시간·예보값을 생성하거나 변경할 권한을 주지 않는다.

## 7. 위치·나침반·시간

Geolocation은 GPS만을 보장하는 API가 아니라 기기의 위치 추정 결과를 반환한다. 위치 정확도와 취득 시각을 함께 저장하고 HTTPS 및 권한 요청에 대응한다. `coords.heading`은 이동 방향이므로 정지한 촬영자의 카메라/휴대폰 방향으로 사용하지 않는다. [S2][S9]

DeviceOrientation은 별도 권한/지원 여부를 확인하고 명시적 클릭 후 요청한다. `requestPermission()`은 모든 브라우저에 동일하게 제공되지 않는다. `alpha` 값을 무조건 진북 방위로 간주하지 않는다. iOS의 webkitCompassHeading 및 absolute orientation 등 지원별 어댑터를 분리한다. 자북/진북 기준이 확인되지 않거나 보정할 수 없으면 ‘근사 방위’로 표시하고 지도 기준을 제공한다. 지자기 편각 보정과 실기기 검증이 없으면 1° 정밀 정렬을 보장하지 않는다. [S3]

heading이 없거나 품질이 나쁘면 나침반이 멈춘 듯 보이게 하지 말고 즉시 수동 모드로 전환한다. 위치와 방위의 정확도는 서로 다른 항목이다. 카메라 자체의 방향은 알 수 없으므로 두 기기의 방향을 사용자가 맞춰야 한다.

시각은 내부 epoch milliseconds/UTC instant로 보관하고 위치의 IANA timezone으로 표시한다. 브라우저 시간대를 위치 시간대로 오인하지 않는다. 고위도에서 일출/일몰이 없는 날, 달의 월출/월몰 중 하나가 없는 날, 23/25시간 DST 날짜를 처리한다. 원본 Date의 invalid/null을 감싸는 정규화가 필요하다. SunCalc의 `utcOffset` 단위는 현재 v2 문서에서 UTC 동쪽 방향의 분이다. DST 전환 날짜의 이벤트는 해당 지역의 하루 경계를 따로 계산해 검증한다. [S1]

## 8. 데이터와 아키텍처

### 권장 스택
Next.js App Router + TypeScript + Tailwind CSS, Google Maps JavaScript API, 천문 어댑터(SunCalc v2를 우선 검토), Zod, Vitest, Playwright. 날씨 클라이언트 캐시는 TanStack Query 또는 기존 프로젝트 표준을 따른다. 상태는 reducer/URL state로 시작하고 불필요한 전역 상태 라이브러리를 늘리지 않는다. 기존 프로젝트가 있으면 의존성을 일괄 업그레이드하지 않는다. [S6][S7]

### 책임 분리
- 브라우저: 정밀 위치, 센서, 지도 UI, 천문 계산, 순수 추천 규칙, 장비·계획 저장.
- 서버 Route Handler: 기상 provider 프록시, 입력 범위 검증, rate limit, cache, 오류 정규화. **기상 서버 API 키는 서버에만 보관한다. Google Maps JS 브라우저 키는 클라이언트에 노출되는 값이므로 HTTP referrer + Maps JavaScript API 제한을 필수로 적용한다.**
- 외부: 기상 API, Google Maps JavaScript API(지도의 렌더링/기본 지도 데이터), 선택적 Places/Geocoding. 기본 지도는 Google Maps만 사용하고 독립 OSM 타일 또는 MapLibre와 섞지 않는다. [S6]

### 후보 데이터 공급자
| 항목 | P0 후보 | 계약/주의 |
|---|---|---|
| 태양·달 | SunCalc | 고정 버전, 각도 단위/기준, 라이선스, 시간대, null 이벤트 검증 [S1] |
| 기상 | Open-Meteo | 모델 기반 현재값/예보; 층별 운량 등 변수 지원 확인 [S4] |
| 지도 렌더러 | Google Maps JavaScript API | Google Cloud 프로젝트, 결제 설정, Maps JavaScript API 허용, 키 제한 [S6][S11] |
| 지도 데이터 | Google Maps 기본 지도/위성 | 지도 ID(Advanced Marker용), 제공자 로고/저작권 표시, 과금/캐시 정책 [S5] |
| 장소 이름 | 초기에는 지도 핀/위경도 | reverse geocoding은 별도 공급자 계약 후 추가 |

Open-Meteo 무료 API의 비상업적 사용 조건과 호출 제한을 상업 서비스에 그대로 적용하지 않는다. 배포 목적에 맞는 라이선스/요금제를 확인한다. 데이터 이용 표기는 유료 이용에서도 확인해야 한다. 원격 기상 provider 장애시 astronomy-only로 동작한다. [S4]

Google 지도의 로고·저작권·지도 데이터 표기를 가리거나 제거하지 않는다. 지도 레이어·오버레이는 지리적 구도 추정선이며 실제 경로를 의미하지 않는다. 지도 및 Places 관련 호출은 계약·비용·개인정보 처리 고지에 반영한다. [S5][S11]

### 기상 데이터 정규화
`temperatureC`, `cloudTotalPct`, `cloudLowPct`, `cloudMidPct`, `cloudHighPct`, `precipProbabilityPct`, `precipMm`, `windMps`, `gustMps`, `visibilityM`를 사용한다. 모든 선택적 값은 `number | null`. `validAt`, `retrievedAt`, `source`, `modelRunAt?`, `timezone`, `spatialResolution?`를 보존한다. 조회 시각을 모델 생산 시각으로 잘못 표시하지 않는다.

요청은 우선 72시간까지 필요한 필드만 가져온다. 15분 cache TTL은 제품 시작값이며 갱신 기준과 데이터 유효시간을 분리한다. 날씨 요청 좌표는 예를 들어 소수점 3자리 수준으로 캐시할 수 있지만 천문·프레임 기하 계산은 사용자가 허용한 원래 좌표로 수행한다. 시간 슬라이더마다 네트워크 요청하지 않는다. hourly 예보를 최근접 구간으로 매칭하고 ‘시간별 예보’임을 유지한다. 빠른 위치 변경 시 AbortController/query key로 이전 요청 결과가 새 위치를 덮지 못하게 한다.

## 9. 실패 상태·개인정보·접근성

| 상태 | 사용자에게 보일 것 | 유지할 기능 |
|---|---|---|
| 위치 거부/timeout | 수동 핀 설정과 재시도 | 선택한 위치의 천문·시간 계획 |
| 센서 미지원/거부 | ‘수동 방향’, 북쪽 고정 지도 | 추천 각도와 화각 |
| 날씨 API 실패/429 | 기준시각과 ‘날씨 불러오지 못함’ | 천문과 기하 추천 |
| 오프라인 | ‘저장된 데이터’, 마지막 조회 시각 | 캐시 데이터, 로컬 계획, 가능한 천문 계산 |
| 지도 타일 실패 | 좌표 입력/나침반 대체 | 방향·시간·장비 |
| 일부 변수 없음 | ‘정보 없음’ | 지원되는 근거만 사용 |
| 해당 일출/월출 없음 | ‘이 날짜에 없음’ | 다음 존재하는 이벤트 탐색 |
| 카메라 프로필 없음 | 센서·렌즈를 직접 입력 | 일반 촬영 조언 |

정확한 위치는 기본적으로 브라우저 메모리에서 처리한다. 위치 저장은 사용자가 계획 저장을 선택할 때만 수행하고 저장 범위와 삭제 방법을 설명한다. 기상과 타일 공급자는 요청 좌표 또는 요청 지역을 받을 수 있음을 알린다. 분석 이벤트/콘솔/서버 로그/LLM 입력에 정밀 위치를 남기지 않는다. 공유 링크는 좌표를 담기 전에 별도 사용자 선택이 필요하다.

야외 접근성을 위해 밝은 기본 배경, 높은 대비, 최소 44px 터치 목표, 최소 16px 본문, 숫자 tabular alignment, 아이콘+텍스트 상태 표시를 사용한다. 색만으로 태양/달/카메라를 구분하지 않는다. prefers-reduced-motion, 키보드 조작, 모달 focus trap/ESC/포커스 복귀를 적용한다. 야간 테마는 다크 계기판과 별개로 나중에 추가할 수 있다.

## 10. 디자인 방향

브랜드: Photography Assistant(가칭), 보조 영문 Photography Assistant. 말투는 사진가 동료처럼 구체적이고 짧게 쓴다. ‘최적화된 AI 솔루션’ 같은 추상적 문구를 피하고 ‘서쪽 하늘이 열려 있는지 확인하세요’처럼 다음 행동을 알려준다.

화면은 날씨 대시보드가 아니라 촬영 현장 도구다. 큰 방위와 한 문장 추천이 주인공이고 날씨는 추천 근거다. 기본은 따뜻한 아이보리 배경, 진한 녹회색 글자, 골드 태양, 청보라 달, 청록 촬영 방향. 과한 glassmorphism·네온·그라데이션·장식적 차트를 피한다.

데스크톱은 **90px의 좁은 아이콘 내비게이션 레일, 53px의 헤더, 넓어진 중앙 계기판과 오른쪽 판단 카드**. 모바일은 **51px 헤더, 작은 주변 여백, 첫 화면에 추천 카드의 시작이 보이는 나침반, 가능한 한 큰 지도 뷰포트**와 하단 4개 탭(현장 / 빛 지도 / 시간 계획 / 내 장비), 핵심 행동 우선. 주요 breakpoints: 390/768/1280 CSS px. 360px 폭도 수평 스크롤 없이 동작해야 한다.

첨부 HTML은 UI/상호작용 프로토타입이다. 천문·날씨·GPS·권한은 시뮬레이션이다. Google Maps 브라우저 키를 설정하면 **지도 바탕과 실제 지리 좌표는 Google Maps JavaScript API로 렌더링**하고, 키가 없거나 오류면 **도식 미리보기/설정 안내**로 명확히 표시한다. 표시된 모든 광선/하늘 정보와 시작 위치는 데모다. 해당 수치를 실제 날짜의 관측값으로 재사용하지 않는다.

## 11. 개발 단계와 완료 기준

### 단계 A — 토대와 화면
프로젝트 확인 → 라우트와 design tokens → fixtures → 현장/지도/시간/장비 → 모바일 동작. 완료: 360/390/768/1440px에서 수평 overflow 없음, 선택 시각·의도·장비가 모든 화면에 일관되게 반영됨.

### 단계 B — 천문과 기하
Angle/FOV 순수 함수와 테스트 → astronomy adapter → 일출/월출 없는 경우 → 시간대. 완료: 독립된 reference fixture와 비교, 각도 기준 확인, 자정/DST/고위도 테스트.

### 단계 C — 실제 데이터와 추천
위치 → 기상 프록시 → 지도 공급자 → 규칙 엔진 → 근거·대체 상태. 완료: 실패·429·오래된 데이터·결측·위치 변경 race test 통과. 실제 날씨 성공 경로와 실패 경로를 분리 검증.

### 단계 D — 실기기와 배포
HTTPS 환경의 iOS Safari/Android Chrome 센서 테스트, 지도와 실제 방위 비교, 개인정보·attribution 점검, PWA/캐시 점검. 자동화 테스트를 통과해도 실제 센서 검증이 끝났다고 보고하지 않는다.

### 필수 테스트
1. 359°→1°가 오른쪽 2°; 1°→359°가 왼쪽 2°; 반대 방향은 180°.
2. 태양 270°에서 노을 270°, 순광 90°, 측광 0°/180°.
3. SunCalc adapter에서 v1 변환의 중복 적용이 없음.
4. 고도 -3°의 달은 ‘수평선 아래’; 낮에 떠 있는 달은 무조건 제외하지 않음.
5. 기상 null과 0%가 다르게 표시되고 추천 근거에 반영됨.
6. FF 35mm 약 54.4°, FF 200mm 약 10.3°; 세로/크롭 반영.
7. 렌즈 최대 개방 F4인데 F1.8을 추천하지 않음.
8. 삼각대가 없고 피사체가 움직이면 장노출을 무조건 권장하지 않음.
9. 사용자 기기 시간대와 촬영 위치 시간대가 달라도 같은 instant를 표시.
10. 일출/월출 누락 및 DST 23/25시간 날짜를 정상 표시.
11. GPS 거부와 compass 거부가 앱 전체를 막지 않음.
12. 위치 변경 후 이전 날씨 응답이 새 위치에 섞이지 않음.
13. 미리보기/오프라인/현재 상태를 구분하고 샘플 데이터를 실시간처럼 표시하지 않음.
14. 모든 버튼/모달/슬라이더 키보드 접근 가능; 모달 포커스 복귀.
15. 로컬 저장이 차단된 브라우저에서도 앱이 crash하지 않음.

## 12. Codex 작업 방법

`CODEX_PROMPT.md`를 시작 지시문으로 사용하고 `AGENTS.md`를 프로젝트 규칙에 병합한다. 기존 AGENTS.md가 있으면 덮어쓰지 않는다. 작은 단계마다 구현 → 테스트 → 실제 실행 결과 기록을 반복한다. design prototype은 시각적 기준이고 `PRD.md`는 제품 의미의 기준이다. 둘이 충돌하면 PRD의 계산/안전/데이터 계약을 우선한다. 실제 공급자가 없으면 mock 모드를 명시하고 production-ready라고 보고하지 않는다. AGENTS.md와 단계별 문서를 이용하는 접근은 Codex의 공식 안내와 부합한다. [S10]
